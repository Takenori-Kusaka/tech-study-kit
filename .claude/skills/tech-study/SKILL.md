# /tech-study — テーマから guide と casestudy を作り、公開するまで

引数（テーマ）: $ARGUMENTS

このスキルは **tech-study-kit**（このリポジトリ。GitHub: Takenori-Kusaka/tech-study-kit）を作業ディレクトリとして動く。考え方は `principles/`、手順は `playbook/`、担当への指示は `prompts/` が正本。成果物は**キットの外**（キットと同じ親ディレクトリの `<slug>-guide` と `<slug>-casestudy`）に作り、キットには過去・今回の成果物を入れない。

## 全体の流れと関門

| 段階 | やること | 関門（ユーザーの承認なしに先へ進まない） |
| --- | --- | --- |
| 0. 準備 | キットを最新に（`git pull`）。`principles/README.md`・`playbook/00-overview.md`・`playbook/08-lessons.md` を読む。ディスク（`df -h`）、`gh auth status`、Node・Python・PowerPoint、WSL の Docker を確認 | — |
| 1. ヒアリング | 複数回の質問で背景・目的・読者・範囲・成果物・制約を固め、`brief.md` にまとめる（下の「ヒアリング」） | **brief の承認** |
| 2. 事前調査と計画 | 1〜2 時間相当の下調べ（標準・製品・事故・権威・書籍の候補）→ Part 構成案・ケーススタディの題材と測り方・書籍・日程・公開先を `plan.md` に | **plan の承認**（ExitPlanMode か AskUserQuestion） |
| 3. リポジトリ作成 | `playbook/01-scoping.md` の「新しいリポジトリを立ち上げる」どおり。brief・plan を `research/` に置いて最初のコミット | — |
| 4. 書籍 | 書籍の候補を示し、ユーザーが購入（Claude in Chrome で購入ページの手前まで案内可。ログイン・支払いは本人）。PDF を受け取り対応表を作る | **購入はユーザー** |
| 5. 調査 | 論点ごとにサブエージェントで並列調査（`prompts/research.md`）→ `research/notes/` | — |
| 6. ガイド | 構成を確定 → デッキ → QA → 3 観点のファクトチェック（`prompts/factcheck.md`）→ 反映 | 構成の確認（Part 一覧を見せる） |
| 7. ケーススタディ | 実験の仕組み（WSL の Docker、`principles/wsl-docker-knowhow.md`）→ N・B・BE と除去実験 → 結果 → スライド → ファクトチェック。一覧表を作るなら `playbook/06` | 題材ごとの重点と見送りの確認 |
| 8. 公開 | GitHub（公開リポジトリ）、Pages、Docswell（ユーザーがログイン → Claude in Chrome でアップロード） | **公開の承認**（リポジトリごと・媒体ごと） |
| 9. 記事 | publishing-hub でブランチ → 執筆 → 原稿ごとに別担当の査読 → PR | **PR のマージはユーザー** |
| 10. 締め | Teams の共有文（`playbook/07` の型。ガイドのリポジトリのリンクを必ず入れる）。新しく得た考え方・教訓をキットの `principles/`・`playbook/08-lessons.md`・`examples/projects.md` に足して push | — |

## ヒアリング（段階 1）

**1 回で済ませない。** AskUserQuestion を 3〜5 回に分け、前の答えを踏まえて次を聞く。毎回、聞いた理由を一言添える。

1. **背景と目的**：なぜ今このテーマか（誰に何を任せるのか、どんな判断に使うか）、読者（既定：新任のテックリーダー）と前提知識、ユーザー自身も学びたいか
2. **焦点の言い換え**：テーマを自分の言葉で言い換えて確かめる（例：「〇〇そのものの解説ではなく、〇〇を使って組織で□□を設計・運用する判断の材料、という理解で合っていますか」）。標準や製品の既定は前提知識として扱うかどうか
3. **範囲**：必ず扱いたい論点（ユーザーの言葉のまま全部拾う）、扱わないこと、対象の製品（3〜5、実機で動かせる OSS を 1 つ以上）、ケーススタディの題材（2〜3）
4. **根拠と成果物**：権威づけの希望（標準・公的機関・業界・日本語の書籍）、書籍を買えるか、成果物（ガイド・ケーススタディ・一覧表・記事）、公開先（GitHub 公開、Pages、Docswell、Zenn・Qiita・note・SNS、Teams）
5. **制約**：期限、使ってよい環境（WSL・Docker・クラウドの有無）、公開してはいけないもの、規模の希望

答えが曖昧・矛盾するときは、その点だけをもう一度聞く。最後に `brief.md` を見せて承認をもらう。

### brief.md の型

```markdown
# <テーマ> 依頼の整理（brief）
## 背景（なぜ今、誰のために）
## 目的（この資料で読者ができるようになること）
## 読者と前提知識
## 焦点（言い換えて確認した一文）
## 扱う論点（ユーザーの言葉のまま）／扱わないこと
## 対象の製品・実装
## ケーススタディの題材（案）
## 根拠の方針（標準・機関・書籍）
## 成果物と公開先
## 制約（期限・環境・公開しないもの）
## 成功の基準（何があれば「完成」か）
## 未決事項
```

## 計画（段階 2）

`plan.md`：slug と 2 つのリポジトリ名、Part 構成案（各 Part の問いと結論の見込み）、ケーススタディの題材・共通の基準の候補・重点・見送り・測り方（実機と模擬）、書籍の候補、調査の分担、レビューの体制、公開の順番、リスクと対策、ユーザーに頼むこと（書籍の購入、ログイン、マージ）。承認を得てから段階 3 へ。

## 進め方の約束

- 進捗の報告は「終わったこと（数字）→ いまやっていること → 次 → 決めてほしいこと」。長い待ちの間も一言
- 外向きの行為（公開、push、Docswell、記事）は毎回確認。publishing-hub は `main` に push しない
- 測っていないものは「未検証」。件数は結果のファイルから数える。表に空欄を残さない
- 道具（デッキの生成器・QA・Web 版・一覧表のスクリプト）は直近の回のリポジトリ（`examples/projects.md`）から新しいリポジトリへコピーし、どこから持ってきたかを README に書く。過去の中身は持ち込まない
- セッションが切れても再開できるように、段階が進むたびに guide リポジトリの `research/plan.md` の「進捗」節を更新してコミットする。再開時はそこから読む
