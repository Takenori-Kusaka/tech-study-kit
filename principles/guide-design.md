# ガイドの設計思想

手順（構成の型、lib.js、QA）は [playbook/03](../playbook/03-guide-deck.md)。ここでは「なぜその構成・書き方にするのか」を書く。

## 1. 読者は「新任のテックリーダー」— 理解するだけでは足りない

ユーザーが想定する読者は、その技術を「ちょっと理解し始めた」段階で、大きなプロジェクトの技術リーダーに任命される人である（RAG の回の言葉では「生半可な理解では不足」）。この読者が必要とするのは次の 4 つ。

1. **判断の材料**：どの手法・設定を、どんな条件で選ぶか（採用判断）。
2. **部下への指示の型**：「このデータならこうなりそうだから、これを検証して」と言えること。RAG のケーススタディには部下への指示テンプレートと、解けなかった問いの「仮説・打ち手・検証方法・完了条件」を入れた。
3. **説明の型**：ステークホルダーに「精度は何%？」「エージェントの正答率は？」と聞かれたときの答え方。単一の数字ではなく、何をどう測ったかで答える。
4. **最初の一歩**：最初の 90 日でやること、チェックリスト、意思決定の記録の型、レビューの観点。

**なぜ**：技術の解説書は世に多い。この資料が価値を持つのは「リーダーとして何を決め、何を任せるか」まで降りているからで、ユーザーが「クリティカルヒット」と評したのもこの部分だった。

## 2. 構成：地図 → 原則 → 製品の違い → 失敗 → 推奨

| 段 | 役割 | なぜこの順か |
| --- | --- | --- |
| 導入・基礎の補足（Part 0〜1） | なぜ今これが問題か、事故の例、前提知識の総点検 | 読者の前提はばらつく。最初に揃えないと後の Part が読めない |
| 地図（全体像） | 既存の手法・クレーム・仕組みを用途ごとに並べる | 独自のものを足す前に、既にあるものを知らないと重複・衝突する（JWT の回で 16 用途の地図を作ったのはこのため） |
| 原則 | 設計の原則と、その根拠 | 製品が変わっても残る判断基準を先に置く |
| 製品ごとの違い | 主要製品の既定・制約・最近の変更 | 原則を実装に落とすときに、どこで食い違うかを示す |
| 失敗・アンチパターン | 事故と、なぜ失敗するか／代わりにどうするか | 「やってはいけないこと」は、成功例より判断に効く |
| 推奨とリーダーの実践 | 採用レーダー、90 日、チェックリスト、根拠の対応表 | 読み終えた人が次の日に動けるように |

各 Part の中も「扉（この Part の問いと結論）→ 問い → 原則 → 製品の違い → 失敗例 → 推奨 → まとめ」で揃える。結論を扉で先に言うのは、テックリーダーが資料を「調べもの」として途中から開くため。

**アンチパターンは厚くする**：RAG の回、公開後にユーザーから「アンチパターンのセクションをもっと増やしてほしい。データ特性と検索したい特性に合わせて使い分けが必要に感じた」と依頼があり、Part 7「アンチパターン大全」（22 枚）を足した（96→118 枚）。万能スキーマの幻想（同じ取込の改善で FMEA は 2/8→7/8 に上がり、特許は 4/6→1/6 に下がった）、汎用リランカーの罠、規模の罠などを、層（データ・索引／検索・生成／システム・組織・規模）ごとに「なぜ失敗するか／代わりにどうするか」の表にした。以後の回は最初から厚く持つ。

## 3. 1 枚 1 メッセージ、1 ステップ 1 枚

- タイトルは結論の文にする（「必須の欠落は拒否。ただし IdP の違いを埋めてから」）。
- ユーザーは「丁寧に細かくステップを刻み、1 ステップ 1 スライドくらい」を求める。長大になってよい（RAG ガイド 125 枚、AgentOps 104 枚、JWT 149 枚）。枚数は目標ではなく、論点を網羅した結果。
- 手を動かす例を入れる：RRF と nDCG、pass@k と pass^k を具体的な数値で計算する。よくある誤読（「5.7%→1.9% は精度 67% 向上ではない」）を取り上げる。
- パイプラインのどの段の話かを示すチップ（パンくず）を各スライドに付ける。

## 4. 根拠の行と発表者ノート

- **全スライドに根拠の行**（仕様／機関／書籍）。書籍は『書名』章・節 p.xx（印刷ページ）。**なぜ**：ユーザーは資料を社内で共有する。読んだ人が「本当か」と思ったとき、その場で原典をたどれることが信頼の条件になる。根拠の行は、ファクトチェックの担当が「この根拠は本当にこの主張を裏づけるか」を照合する単位にもなる。
- **発表者ノートは、読むだけで発表できる量**：スライドに載せられなかった説明、但し書き、数字の条件を書く。JWT の回では、ケーススタディで分かったこと（Keycloak のトークン交換で宛先を付け替えられた、など）をノートに書き足してガイドを更新した。
- **補足と模式図は明示する**：元資料の外から足した内容は「補足」、実測でない図は「傾向を示す説明用の図」とスライドに書く。

## 5. 言葉の規則

- **平易な日本語**：漢語・カタカナ語を減らし、主語と述語を近づける。1 文を短くする（記事の lint では 150 字超の文で止まる）。
- **用語は初出で定義する**：記事の読者役の点検で「AgentOps がどこにも定義されていない」「注入（injection）と実行ブローカーが説明なしに使われている」と指摘された。RAG のガイドでも hub/spoke、federated、MRR、nDCG@10、MCP、oversharing、Oracle Context に定義を足した。ファイル冒頭の用語表で表記を揃える。
- **紛らわしい略語を避ける**：RAG のガイドでは ACL をアクセス権限の意味で使っていたので、学会の「ACL 2021」は著者名（Reimers & Gurevych 2021）に置き換えた。
- **ユーザーの用語に合わせる**：「属性」は claim の訳として使わない（一覧表の列名で直した）。
- **煽らない**：「革命的」「必須」などの強い言葉を使わない。原典より強く言わない（SHOULD を MUST と書かない、推奨を標準のように書かない）。
- **数字に条件を付ける**：「約 2 倍」ではなく「寿命 15 分で約 2.2 倍、60 分で約 4 倍」。どの条件で、何回測ったかを書く。
- **製品名には版と日付**：「Keycloak 26.8」「2026 年 11 月時点」。
- **応答と資料は日本語**：英語に流れたとき、ユーザーは「日本語で」と 2 回訂正した。

## 6. スライド間の矛盾をなくす

点検で多かったのは、スライド単体では正しいが、別のスライドと食い違うものだった。

- 「文脈を足すほど悪くなる」の隣に「DeNA は 20 件まで改善した」→ 上り坂と下り坂として説明し、「どこで折れるかは測る」に揃えた。
- 「圧縮で EM が改善」をリスクの題のスライドに置いていた → 理由を書いた。
- JWT の共通の基準で「トークンとクレームをログに残さない」と書き、別のスライドでは発行者・宛先を残すよう勧めていた → NIST IR 8587 が禁じるのは「トークン全文と、含まれる個人情報」なので、そう直した。
- 委任の深さを「見送り」にしつつ「上限は組織の規則で決める」とも書いていた → 「標準による強制は見送り、当面は組織の規則と入口の検査で上限を設ける」に揃えた。

**なぜ**：テックリーダーは資料の一部を抜いて部下に渡す。矛盾があると、渡した側の判断が揺れる。

## 7. ガイドとケーススタディは往復させる

- ケーススタディは「ガイドの主張を実験で確かめる」ものとして作る（AgentOps v2 の設計原則）。
- ケーススタディで分かったことは、ガイドに戻す。JWT の回では、Keycloak がリフレッシュで属性とロールを読み直すこと（ガイドで「未確認」としていた点）、トークン交換で宛先を付け替えられること、必須クレームの欠落拒否には IdP ごとの扱いが要ること、契約テストで見つからない変更があることを、ガイドの該当スライドに足した。
- ガイドの「足す前の質問」「アンチパターン」を、ケーススタディで測る対象にするため、順番は「ガイド → ケーススタディ」にする（JWT の回でユーザーに確認して決めた）。
