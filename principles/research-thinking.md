# 調査の考え方 — 新しい技術スタックに向き合うとき

手順（情報源の優先順位、ノートの型）は [playbook/02](../playbook/02-research.md)。ここでは、その裏にある判断の理由を書く。

## 1. 最初に「読者の本当の問い」を言い当てる

技術の解説を集めることが目的ではない。読者（新任のテックリーダー）が、その技術を使うプロジェクトで**何を決め、何を部下に指示し、何を説明しなければならないか**が問いである。

- **RAG の回**：ユーザーが懸念したのは「表面上の理解に留まり、起きたことに仮説を立てられない」「部下に『このデータならこうなりそうだから、これを検証して』と指示できない」ことだった。だから手法の一覧ではなく「どのデータに何が効くか」を実測する方向に寄せた。
- **AgentOps の回**：ユーザーは「RAG は回答のための入力を良くするもので、応答を直接は良くしない」と位置づけ、その対になる資料を求めた。前の回との関係（何を補うのか）が問いの一部になる。
- **JWT の回**：調査を始めた時点で、こちらは「標準クレームを正しく検証する話」に寄せていた。ユーザーの訂正は「標準の OIDC や SAML のクレームを知りたいのではなく、あらゆるサービス間で共用するカスタムクレームの設計の話」。ただし続けて「重複させないために、標準と各社 IdP の知識は基礎として重要」と補足があった。主題（独自クレームの設計と運用）と前提知識（標準と製品の既定）を分けて扱うのが正解だった。

**なぜ**：問いを取り違えると、調査が正確でも資料は役に立たない。JWT の回では、言い直しを受けてから調査を 2 本足し、目次を組み直した。最初に言い換えて確かめていれば、その手戻りはもっと小さかった。

**どうするか**：最初の返答で「〇〇そのものの解説ではなく、〇〇を使って□□を設計・運用する判断の材料、という理解で合っていますか」と言い換える。ユーザーが挙げた論点はユーザーの言葉のまま全部書き出し、どの Part で答えるかを対応づける（漏れを見つけるため）。

## 2. 4 つの層を分けて調べる

同じ話題でも、次の 4 つは性質が違う。混ぜると「標準が求めていること」と「ある製品がそうしているだけのこと」の区別がつかなくなる。

| 層 | 問い | 例（JWT の回） |
| --- | --- | --- |
| 標準が言うこと | 何が規範（MUST）で、何が推奨か。草案か最終版か | RFC 7519 の「未知のクレームは無視する」には「アプリケーションが特に定めない限り」という条件がある |
| 製品がすること | 既定値・制限・名前。いつの版か | Entra の AT の既定寿命は 60〜90 分のランダム値。Cognito の AT には aud が無い |
| 事故が示すこと | 実際に何が壊れ、原因はどの取り決めの欠陥か | Storm-0558 は「誰が発行者を検証するか」の欠陥。CVE-2025-55241 は tid の照合漏れ |
| 権威が勧めること | 公的機関・業界の指針の位置づけ（規範か任意か） | NIST IR 8587 は連邦機関向けの実装推奨で、民間には任意 |

これに「学術の結果」と「書籍の考え方」が加わる。

**なぜ**：ガイドの読者は、スライドの一文を根拠に設計を決める。「標準がそう決めている」と「ある製品の既定がそうなっている」では、別の製品に移ったときの扱いが正反対になる。

**つまずき例**：
- 「RFC 9700 と FAPI 2.0 はリフレッシュトークンのローテーションで逆を求める」と書いたが、言い過ぎだった。対象が違う（公開クライアントと機密クライアント）ので、送信者制約を使えば両方を満たせる。二つの仕様を「正反対」と書く前に、前提（誰に向けた規定か）を確かめる。
- 「下流のトークンは上流より強くしない」は RFC 8693 では推奨にとどまり、強制する仕組みは仕様にない。だから「組織の規則と検証で担保する」が結論になる。

## 3. 情報源の重みづけ

### 何を確かめてから使うか

- **版と状態**：草案は版番号を書き、結論の根拠にしない。「最終版」と「正誤表の承認」を取り違えない（OpenID Identity Assurance は 2024 年に確定、2026 年 7 月は正誤表）。草案は名前が変わる（Transaction Tokens の `purp`→`scope`、`azd`→`tctx`）。古い名前の解説記事が多いので、最新の草案で書く。
- **規範か任意か**：公的機関の文書でも、対象（連邦機関のみ、保証レベルが高い場合のみ）を確かめる。NIST SP 800-63C-4 が単一の宛先を必須にするのは FAL2 以上に限る。
- **何を測った数字か**：論文の数字は、タスクの種類まで読む。Late Chunking は、元論文（多数の文書から探すコーパス検索、BEIR）では +1.9pt、2026 年の比較（1 冊の中を探す文書内検索）では全条件で低下した。「元論文が誤り」ではなく「効く場面と効かない場面がある」。Contextual Retrieval の −49% は「埋め込みのみ」が基準なので、BM25 を足した効果も含む。
- **観察か比較か**：Anthropic の「文脈は 50〜100 トークン」は、普段観察した値で、長さを比べた実験ではない。比べた実験が見つかるまでは「目安」として扱う。
- **ベンダーと事例の数字**：運用事例の数字（企業のブログ、ベンダーの報告）は「自己申告」と明記する。規模の影響（コーパスを 5,000 件から 51 万件に増やすと Recall@10 が下がる）はベンダーの報告として引く。パナソニックの「788,000 時間」は RAG 単体ではなく全体の効果だった。
- **業界の権威の分類**：Thoughtworks Technology Radar の位置（GraphRAG は Hold ではなく Trial）など、分類は原典で確かめる。

### 見つからないことも結論になる

「一次資料に無い」と確かめられたことは、それ自体がガイドの内容になる。

- アクセストークンの推奨寿命の数値は、一次資料に見つからなかった。だから寿命の章は公的機関の指針と、ケーススタディの試算を根拠にした。
- SAML の属性と JWT のクレームの対応を規範として定めた標準は無かった。さらに Entra は SAML の AuthnContextClassRef を `acr` ではなく `amr` に写す。IdP をまたいで正規化するときの落とし穴として書いた。
- テナント・組織、同意・目的を表すクレームは IANA の登録簿に無い（2026-10-28 版で確認）。だから組織の独自クレームとして設計する代表例になる。

**なぜ**：「見つからなかった」を書かないと、読者は「どこかに標準があるはず」と探し続けるか、ある製品の名前を標準と思い込む。

## 4. ユーザーが渡す元資料は「草案」として扱う

RAG と AgentOps の回は、ユーザーが用意した技術レポート（Markdown）が出発点だった。

- レポートの数字は、別の担当に一次資料で照合させた。AgentOps の回はほぼ一致したが、条件（MCP 仕様の版、GEPA のどの版の数字か、Agent-as-a-Judge の評価条件）を直した。
- レポートに無いことを足したときは「補足」と明記した（RAG の回：7 つの失敗点、日本語の埋め込みモデル、BM25 の日本語処理、ANN と権限フィルタ）。
- 調査ノートは「AI が作ったもので、数字が食い違うときはスライドを正とする」と README に書いた。

**なぜ**：元資料をそのまま信じると、元資料の誤りがガイドの権威を借りて広がる。逆に、元資料と違うことを黙って書くと、ユーザーが元資料と照合したときに混乱する。

## 5. 書籍の選び方と使い方

ユーザーは「書籍に準拠している」と言える権威を求める（Thoughtworks や IPA のような「世界的な権威があればあるほどいい」）。書籍は次の観点で選ぶ。

| 観点 | JWT の回の判断 |
| --- | --- |
| 著者・監訳者の立場 | 『実践 Keycloak』は Keycloak のプロジェクトリーダーが著者、訳者に Keycloak のメンテナー。『デジタルアイデンティティのすべて』は監訳者が OpenID ファウンデーション・ジャパンの代表理事。『OpenID Connect入門』は監修者が同理事 |
| 新しさ | 『OAuth徹底入門』（2019）は RFC 9068 や DPoP より前。標準の部分は RFC と公式和訳で足りるので外した |
| 対象の版 | 『実践 Keycloak』日本語版は Keycloak 18.0.2 が前提。現行 26 系と違う 12 項目を「古い記述」として印を付けた（例：24 以降は定義していない利用者属性を既定で使えない） |
| 本の立場 | 『デジタルアイデンティティのすべて』は概念の本で、アクセストークンを不透明な文字列として扱い、OIDC に批判的（重心は自己主権型）。だから「本書の考え方に沿う」と書き、「本書が JWT についてそう述べている」とは書かない。引用には「（考え方）」を付けた |
| 現行仕様との食い違い | 『セキュアAPI』は現行仕様と食い違う記述が 14 件（ログの例がトークンを含むヘッダーをそのまま記録、寿命を「1〜24 時間」など）。『OpenID Connect入門』の寿命「まず 30 分」は著者自身が根拠がないと書いている。こうした記述は根拠として引かない |
| 入手しやすさ | DRM なしの PDF で買える本は、本文を検索して章・節・ページを正確に引ける |
| 埋まらない部分 | マルチテナント、トークン交換と委任、AI エージェント、サービス間の文脈、データ層は日本語の書籍が見つからなかった。NIST・OWASP・デジタル庁・RFC で裏づけた（政府標準や国際団体の文書なので、書籍より強い根拠になる） |

**冊数の判断**：「3 冊全部要るか、1 冊で十分か」と聞かれたら、各冊が埋める論点と、外したときに何が困るかで答える。JWT の回は 2 冊で始め、標準のトークンと検証の部分が弱いと分かったので 1 冊足し、任意の 1 冊を「予算があれば」として示した（最終 4 冊）。

**読み方**：
- 1 冊につき 1 人の担当に、ガイドの論点ごとの「章・節・印刷ページ・要約（自分の言葉）・使い方（準拠／考え方のみ）」の対応表を作らせる。
- 印刷ページと PDF のページはずれる（『実践 Keycloak』は PDF のページ＝印刷ページ＋23）。本文中のノンブルで記録する。
- 書籍の章ごとの対応表は本の内容の言い換えなので、公開リポジトリからは外した（著作権への配慮）。公開するのは書名・章節・ページと短い要約だけ。

## 6. 調査の進め方の考え方

- **論点ごとに担当を分けて並列にする**：JWT の回は 8 本（標準、IdP、事故と攻撃、公的機関、独自クレームの実例、データ層、マイクロサービスの流れ、書籍）。1 本ずつ終わるたびに、ガイドに効く結果を短く報告した。
- **ユーザーの追加論点はその場で調査を足す**：「アクセス制御、証跡、他クレームのパース方法」と言われて、流れ全体とデータ層の 2 本を足した。
- **実データの構造を調べてから合成する**：RAG の回は「実際の企業が公開している実データをもとに」と求められた。メーカーの取扱説明書、AIAG-VDA の FMEA 様式、日本の特許、公開の不具合 DB を調べ、**構造だけ**を架空企業の合成データで再現した（内容は創作、実在企業の文書は使わない）。
- **事例は「どうやって乗り越えたか」まで読む**：全社汎用 RAG の成功例（Uber、LinkedIn、Grab、Pinterest など）は、どれも「1 つの汎用索引を最適化した」わけではなかった。共通点（領域を絞る、ルーターと専門の検索器、取込への投資、索引の持ち方をソースごとに選ぶ）を抜き出すと、ユーザーの直感（汎用だと rerank まで含めて最適化が難しい）への根拠ある答えになった。

## 7. すべてに日付を付ける

- 調査日を outline、ノート、README、記事に書く（「2026 年 11 月時点」）。
- 製品名・仕様名・数値には版と日付を添える（「Keycloak 26.8」「MCP 2026-07-28 版」「IANA 登録簿 2026-10-28 版」）。
- 相対的な時期の言葉（「最近の」「2024〜2026 年の比較では」）は、スライドでは避けるか、原典の年を書く。

**なぜ**：この領域の仕様と製品は数か月で変わる（Keycloak の `session_state` クレームの削除、草案の改名）。日付の無い主張は、半年後には誤りか正しいか判断できない。
