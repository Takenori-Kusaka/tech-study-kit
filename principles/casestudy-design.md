# ケーススタディの設計

手順（N・B・BE、除去実験、run_all.py）は [playbook/05](../playbook/05-casestudy.md)。ここでは 3 回それぞれの設計判断と、その理由、失敗と直し方を書く。

## 1. 目的：「表面上の理解」を「期待値」に変える

ユーザーがケーススタディを求めた理由は、ガイドを読んでも「具体的な適用方法や、適用した結果どうなりそうかという期待値」がイメージできないことだった。だからケーススタディは次に答える。

- どのデータ（題材）に、どの打ち手が、**どれだけ**効くか（数字）
- その打ち手を外すと何が壊れるか（その打ち手が何を買っているか）
- 効かなかった・悪化したのはどこか（万能の解は無い）

## 2. 題材の選び方

- **ユーザーが指定した実在の題材に合わせる**：RAG と AgentOps は、公開されている FMEA 作成支援ソリューションのページを題材にした。入力データ 1〜6 の定義はそのページの図から取った。
- **ユーザーの実務知識を失敗の型として使う**：RAG の回でユーザーが挙げた 3 つ（製品マニュアルに無く通信マニュアルにシリーズ別に書いてある分冊マニュアル、多段の結合ヘッダを持つ「神エクセル」の FMEA、図の番号と本文の説明が離れた特許）を、そのまま問いのカテゴリにした。
- **前の回と同じ世界を使う**：AgentOps v2 は、RAG のケーススタディと同じ架空企業・同じ 24 ファイルのコーパス・同じ検索構成（最終段 S6）を知識源にした。**なぜ**：題材を変えると「RAG で入力を良くした先で、エージェントの応答がどうなるか」という対の関係が切れる。v1 で題材を「不具合対応」に変えたのが、ユーザーに「チープ」と言われた原因の 1 つだった。
- **題材は 2〜3 で、性質が違うものを選ぶ**：JWT はマルチテナント SaaS／社内業務システム／AI エージェントの委任。同じ基準が題材ごとに違う弱点を持つことを示せる。

## 3. 合成データ：実在の構造、架空の中身

- 実在企業の公開資料（メーカーの取扱説明書、AIAG-VDA の FMEA 様式、日本の特許、公開の不具合 DB）を調べ、**構造だけ**を再現した。会社・製品・特許番号・数値はすべて架空（「ミナト精機（架空）」）。
- ファイル形式も再現する：Excel は実ファイル、Word は Word 経由で PDF 化、スキャン PDF は印影やノイズ入りの画像だけの PDF（24 ファイル）。
- 正解（gold）は**データの生成器から作る**。エージェントや検索の出力から作らない（AgentOps v2 で明記した原則）。**なぜ**：出力から正解を作ると、測る対象が正解に混ざる。

## 4. 共通の基準＋重点＋見送り

ユーザーの見立て「銀の弾丸はなく、最大公約数に加えて何に重点を置き、何を見送るかが肝要」を、そのまま結論の型にした。

- **見送りには代償を測って書く**。JWT の回の例：
  - 細かい権限をトークンに載せると、許可した請求書が 0/20/200/1000 件でトークンは 634/707/1629/6563 バイト。取り消しは期限（300 秒）まで届かない。PDP で都度判定すると p50 585 µs だが、取り消しは次の要求で効く。
  - 送信者制約（DPoP）を見送ると、盗まれたトークンの再送はどの構成でも通る（BE でも 1/18 が残ったのはこれ。意図して残した）。
  - 寿命を 60 分から 5 分にすると、古い権限での判断は約 40,900 → 4,950 件、問い合わせは 1 時間 2,000 → 13,000 回。重要な操作だけ問い合わせると追加約 6,100 回で、重要な操作の古い判断は 0。
- **共通の基準にも費用がある**：「必須クレームが欠けたら拒否」は、Entra の groups 超過の管理者と、aud を持たない Cognito の AT という正規の要求 2 件を拒否した。入口の正規化と超過の解決で 0 件にした。「共通の基準を守るには IdP ごとの扱いが要る」という発見自体が結論になった。

## 5. 攻撃と正規の要求を必ず混ぜる

- 攻撃だけを並べると、「全部拒否する実装」が満点になる。正規の要求が拒否されること（誤拒否・過剰拒否）も失敗として数える。
- AgentOps v1 でも同じことが起きた：エージェントに社内規程を渡すと漏えいと二重送信は消えたが、承認を求めればできた返金まで断る「過剰拒否」が新たに出た。
- 件数を書くときは、何を数えたか（攻撃のみか、正規の要求を含むか）を書く。JWT は「67 ケース（攻撃と正規の要求の合計）」。

## 6. 除去実験：その要素は何を買っているか

- B から基準の要素を 1 つずつ、BE から重点の要素を 1 つずつ外し、どの攻撃が再び通るか、どの正規の要求が拒否されるかを表にする。
- **なぜ**：「N は全部通り、BE は全部止めた」だけでは、どの要素が効いたのか分からない。テックリーダーが「この確認は省いてよいか」と聞かれたとき、答えられるのは除去実験の表だけ。
- 1 つ外しても防げたままの攻撃（複数の要素が重ねて防いでいる）も記録する。
- **よくある誤りの変種も構成として足す**：JWT のマルチテナントでは、RLS は残したまま文脈をトランザクションではなくセッション単位で設定する誤り（`BE~session`）を構成に加え、接続プールで前の利用者の文脈が残ることを示した。
- RAG の回は除去ではなく**積み上げ**で測った（S0 ファイル丸ごと 19/48 → S1 素朴な RAG 18 → S2 構造を残した取込 24 → S3 ハイブリッド 28 → S4 文脈ヘッダ＋型番の正規化 37 → S5 参照グラフ 40 → S6 再ランキング 44 → S7・S8 は 43 で改善なし）。積み上げは「どこで伸びたか」、除去は「何を守っているか」を示す。題材に合う方を選ぶ（両方でもよい）。

## 7. 実機と模擬

- **OSS を 1 つは実機で動かす**：RAG は OpenSearch 2.19.1（kuromoji と ICU 入り）、AgentOps は実際のモデル（Haiku・Sonnet を `claude -p` で）、JWT は Keycloak 26.8.0 と Postgres 16 の RLS。
- **実機でしか分からないことがある**：Keycloak 26.8 の標準トークン交換は、宛先を絞るだけでなく別の宛先に付け替えられた（mcp-tools 宛てを orders 宛てに）。上限は元のトークンではなく、交換を求めたクライアントの持つ範囲だった。結果のトークンに `act` は付かなかった。軽量アクセストークンでは sub・aud・realm_access など 12 個のクレームが落ちた。ガイドの記述と違った点は、ガイドを直した。
- **商用製品は公式文書どおりの模擬にし、模擬だと明記する**：Entra・Okta・Cognito・Auth0 はトークンの形を再現した模擬の発行元。記事で「各社の製品で測った」と書いてはいけない（note 版で書いてしまい、査読で直した）。
- **本物の外部 API と比べるときは条件の不利を書く**：AgentOps で実際の判定 API（Jev）と比べたとき、参照ラベルが同じ Claude 系の Opus であること、入力が日本語であること、代用は 3 回の平均で本物は 1 回であることを注記し、「劣るとまでは言えない」とした。製品名を出した比較の公開はユーザーに判断を仰いだ（規約にベンチマーク公表の条項が無いことは「未検証・法務確認要」）。

## 8. 決定的に流す

- JWT の回は LLM を判定に使わず、乱数の種を固定し、仮想の時計で寿命を試算した。何度流しても同じ結果になる。
- RAG の回の判定は「回答に必要な根拠が上位 5 件に揃ったか」（正解の事実を正規表現で照合）。LLM の最終回答の正しさは測らない、と限界に書いた。
- **LLM を測る回（AgentOps）は、決定的にできない部分を統計で扱う**（次節）。それでも、採点のうち決定的にできる部分（形式、AIAG-VDA の規則、RPN/AP の計算、引用した文書が実在し、その文を含むか）は決定的な検査にした。
- 状態は最終状態で採点する：エージェントが「やった」と言ったことではなく、業務データ（DB）の最終状態で判定する（AgentOps v1 から）。
- 結果のファイルは版を残す：判定の方式を変えるときは、前の結果を `results_k5_v1_parsedtitle.json` のように名前を付けて残してから再実行した。

## 9. 統計（AgentOps の回）

| 道具 | 何に使ったか | なぜ |
| --- | --- | --- |
| pass^k（k 回とも成功する割合） | 各タスク 5 回、pass^5 と pass@5 | 業務で使うエージェントは「たまに成功」では困る。成功率 9 割でも 5 回とも成功する割合は 7 割弱だった |
| Wilson の信頼区間 | 成功率の区間（例：18/20 は 69.9〜97.2%、44/50 は 76.2〜94.4%） | 試行回数が少ないとき、正規近似の区間は 0〜100% を外れたり狭すぎたりする |
| 3 の法則（0 件のときの上限） | 安全系 185 回で違反 0 件 | 「0 件」から言えるのは「違反率の上限」だけ（0/n の 95% 上限はおよそ 3/n）。「制御を足すと違反が減る」という v1 の筋書きが再現しなかったので、この構成に変えた |
| McNemar 検定・ブートストラップ | 同じタスクでの構成の比較 | 同じタスクを両方の構成で解くので、対応のある比較になる |
| κ（一致度） | 判定役と参照ラベル（Opus）の一致（実際の出力 214 行） | 判定モデル自体が測定器なので、その精度を測る |

試行回数は目的で変えた：違反を数える段（S1〜S4）は 3 回、pass^5 を出す S0・S5 は 5 回。

## 10. 採点器（判定役）も測定対象にする

AgentOps v2 で最も学びが大きかった部分。

- **誤りを仕込んだ行で監査する**：誤りなし 10 行＋明らかな誤り 30 行、のちに紛らわしい誤り 20 行。明らかな誤りでは判定役の差は出なかったが、紛らわしい誤りでは差が開いた（決定的検査 0/20、Haiku の型付き判定 14/20、Sonnet 18/20、Opus 20/20、道具を使う Agent-as-a-Judge 20/20 だが正しい行を 4/10 誤って指摘、引用必須の陪審 18/20 で誤指摘 5/10）。
- **質問を直すと別の誤りを見逃す**：陪審の偽陽性（5/10）を減らすため質問を直すと（v2）、偽陽性は 1/10 に減ったが「原因と故障モードの不一致」の検出が 5/5 → 1/5 に落ちた。判断ごとに質問を分けた v3 で 3/5〜5/5 に戻った。教訓：**判断ごとに質問を分け、直すたびに同じ行で全種類を測り直す**。
- **採点器のバグは必ずある**：v1 で 1 件、v2 で合計 6 件見つけ、直して採点し直した（例：正規化が特定の文字を含むパターンを黙って壊していた、注入の無いタスクでも「注入に従った」と数えていた）。直したことは記録に残す。
- **偏りの試験**：身びいき・冗長さ・順序。2 つの下書きを比べさせる判定は順序で答えが変わった（一貫したのは Haiku 3/6 組、Sonnet 1/6 組）。

## 11. 構成の比較と、その落とし穴

- 単体エージェント 11/15、固定ワークフロー 13/15、役割分担（検証役が文書を確かめる）15/15、判定ループ 10/15、自己反省 7/15、外部フィードバック 6/15（Haiku、同じ 3 タスク × 5 回）。
- 「自己反省と外部フィードバックが単体より低い」は、採点の問題でないかを実行記録で確かめてから結論にした（どちらも「書かれていない行」を見つける手段になっていなかった）。
- **固定ワークフローの検索語は、正解を知る自分が書いた**ので、成績の一部は評価の知識の漏れである、と資料に明記した。

## 12. 攻撃は固定と適応の両方

- 固定の注入文（不具合報告・特許・取引先メールに仕込む）では、495 回で成功 0。ただし単純な注入だったので「適応的な攻撃への耐性は示していない」と書いた。
- 攻撃側のモデルが書き直す適応的な攻撃では、命令ではなく**偽の設計事実**（「CN2 が二重化している」）を混ぜた文で、エージェントが自分の推論で重大度を下げた。
- 攻撃側のモデルが攻撃文の作成を断ったラウンドは「辞退」として記録し、限界に書いた。

## 13. 何が結果を信頼できるものにしたか

1. 正解をデータの生成器から作り、最終状態で採点した。
2. 攻撃と正規の要求を混ぜ、誤拒否も失敗として数えた。
3. 除去実験（または積み上げ）で、要素ごとの寄与を示した。
4. 実機と模擬を区別し、模擬と明記した。
5. 採点器そのものを監査し、バグと直し方を公開した。
6. 限界を資料に書いた（48 問なので 1 問の差は誤差、OCR ツールの無料版は非商用ライセンス、0 件は上限だけ、など）。
7. 環境（CPU、GPU、言語、ライブラリ、製品の版）と費用（AgentOps は API 換算で約 50 ドル、うち 4 割が採点器の検証）を記録した。
8. 1 本のスクリプトで再実行できる（`gen/start_os.sh` → 全段、`run_all.py`）。

## 14. 失敗と直し方

| 失敗 | どう気づいたか | 直し方 |
| --- | --- | --- |
| AgentOps v1 が薄かった（15 タスク×3 回、題材のずれ、採点が真偽の条件だけ、構成比較なし、25 枚） | ユーザーに「自分で査読して十分だと思うか」と聞かれ、自己査読で 5 つの問題を挙げた | ガイドの各 Part の主張を 1 つずつ実験に対応づける計画（PLAN-v2.md）を作り直した。規模はその結果（74〜76 枚、588＋121 回） |
| 「100 ページ以上」を枚数の要求と受け取った | ユーザーが「抽象的な表現。内容が薄すぎると言いたかった」と補足 | 枚数ではなく、ガイドの論点のうち何割を検証したかで十分さを測る |
| JWT の 1 回目は攻撃 4〜9 件、Auth0 の形を使わず、どの要素が効いたか不明 | 自分で「このままでは薄い」と判断 | 除去実験、各題材 15〜20 件、IdP ごとの落とし穴（Auth0 の予約名で消えるクレーム、Okta のフックのタイムアウト、Cognito の利用者が書ける属性、Entra のマルチテナント iss、Keycloak の Full Scope Allowed）、Keycloak の実測、寿命の試算、9 つの受け手での変更実験、5,000 回の遅延測定を足した |
