# 検証の原則

手順（3 観点のファクトチェック、記録の場所）は [playbook/04](../playbook/04-factcheck.md)、記事の査読は [playbook/07](../playbook/07-publish.md)。ここでは「何をもって検証したと言えるか」の基準を書く。

## 1. 「検証済み」と言えるもの

| 言ってよい | 条件 |
| --- | --- |
| 一次資料で確認済み | 自分か担当が、その文書（RFC・公式文書・報告書）を実際に開き、節や行を特定した。調査メモに書いてあるだけでは足りない |
| 実測済み | ケーススタディの実験で、条件・回数・環境を記録して測った |
| 目視で確認済み | 実際に描画・公開されたものを見た。**どの版を見たか**まで言う |
| 未検証 | 上のどれでもない。推奨や推論として書くなら「未検証」と明記する |

**なぜ**：資料は「権威に準拠している」として組織の中で共有される。一文でも「確認したつもり」が混じると、資料全体の信頼が落ちる。

**範囲を正直に言う例**：
- 「最終版のスライドは全体検査（はみ出し 0 件）を通し、直した箇所は画像で確認した。74 枚すべてを通しで見直してはいない」
- 「公開ページで v2 になっていることを確認したのは、上げ直す前の版。上げ直した版は、編集画面で表紙が v2 になっているところまで見た」
- 一覧表の行：323 行のうち 319 行は一次資料で確認、4 行は「未確認」の印を付けた。

## 2. 書いた本人と別の担当がレビューする

| 対象 | 担当の分け方 | 回 |
| --- | --- | --- |
| デッキの事実 | 観点で 3 人（標準／製品／書籍と機関） | JWT |
| デッキの読みやすさ | 枚数で 3 人に 1/3 ずつ、前提を知らない新人として読む | RAG（約 45 か所）、AgentOps（約 50 か所） |
| 元資料の数字 | 検証担当が一次資料と照合 | AgentOps |
| 一覧表の列 | 列の過不足の自己レビュー（調査と並行） | JWT |
| 一覧表の判定 | 判定を書いた担当とは別の担当が、必須・採用・禁止は全件、ほかは全分類から 120 行以上 | JWT（9 種類の指摘、「このままの公開は勧めない。直せば公開できる」） |
| 記事 | 原稿ごとに「事実の査読」と「読者役（前提なし）」を別の担当 | 3 回とも |

**なぜ観点を分けるか**：1 人に「全部見て」と頼むと、目につきやすい表記ゆれに注意が集まり、仕様の節番号の誤りのような深い誤りを見落とす。観点を分けると、それぞれが一次資料まで降りる。

**なぜ読みやすさを別に見るか**：事実が正しくても、新任のリーダーが読み解けなければ使われない。ユーザー自身が「人間がいまいち読み解ききれないスライドがある」と指摘したのがきっかけ。

## 3. レビューの指摘も確かめる

担当（サブエージェント）の指摘にも誤りがある。重要な指摘は、反映する前に自分で一次資料を開く。

- JWT の回：修正の担当が「調査メモに記述が無く、指摘を信頼して反映した」とした 5 点を、自分で一次資料で確かめた（OpenID Identity Assurance の確定年、Entra の AT の既定寿命、MCP の RT ローテーション必須、Transaction Tokens は応答に RT を含めない、ライブラリの exp の既定）。5 点とも正しかったが、確かめたことを記録した。
- 査読の出力が壊れていたら（YAML として読めない、ファイルに無い文を引用している）、書いた担当に直させる。取りまとめ役が中身を書き換えない。AgentOps の回では、読者役がツールの描画にしか無い文を引用していたので、「ファイルにある文だけを引用する」と指示して読者役だけやり直した。
- 判定の点検の指摘も、構成と照らして確かめる（「入口で読んで ID トークンに写す」は、入口が ID トークンを受け取らない構成と矛盾する、など）。

## 4. 言う前に測る

- 主張はできる限り実験で裏づける。ガイドで「未確認」としていたことを、ケーススタディで確かめた（Keycloak がリフレッシュで属性とロールを読み直す）。
- 実験がガイドと違ったら、ガイドを直す（Keycloak 26.8 の交換で `act` が付かない、宛先を付け替えられる）。
- **測っていない推奨は「未検証」と書く**：DPoP・送信者制約は、一覧表の判定（「推奨。実験では未検証」）、ケーススタディのスライド、記事の 3 か所に書き、見直し条件に「盗まれたトークンを再送する攻撃のケースを足して効果を測る」を入れた。
- **推論は推論と書く**：Late Chunking の「使う／やめる」の表は、文書の種類ごとに直接検証した論文が見つからず、2 つの結果と仕組みから推論したもの。スライドにそう書き、実務での確かめ方（評価セットを「どの文書か」型と「文書内のどこか」型に分けて比べる）を添えた。

## 5. 件数は結果のファイルから数える

- JWT の README に「全 72 ケース」と書いたが、結果のファイルを数えると 67 件だった（作業中の見込みの数字が残っていた）。
- AgentOps の表紙は実行回数 513 回のままで、本文の 588 回と食い違っていた（公開後に気づき、上げ直した）。
- 記事の数字は正本（リポジトリの results）から引く。「約 2 倍」のように条件を落とさない。部分的な結果を全体として書かない（契約テストで見つかったのは壊れた 5 つの受け手のうち 3 つ）。

**どうするか**：README・表紙・記事・共有文の数字は、最後に結果のファイルから数え直してから出す。数字が出てくる場所を grep で全部洗い出し、同じ値か確かめる。

## 6. 繰り返し出た誤りの型

3 回のファクトチェックと査読で繰り返し出たもの。次の回はレビューの観点に最初から入れる。

1. **ライブラリ・製品の既定値の古さ**：exp が無いトークンを通すのは golang-jwt だけと書いたが、jsonwebtoken・jose・PyJWT も通す。既定で必須にするのは Microsoft.IdentityModel だけだった。
2. **仕様の順序・出典の取り違え**：「RFC 9068 がこの検証順序を定める」→ RFC 9068 では typ の確認が最初。スライドの並びは資料の整理だと明記。利用者とクライアントの sub を区別する MUST の出典は RFC 9068 ではなく RFC 9700 §4.15.1（しかも条件付き）。
3. **最終版と正誤表、草案の版の取り違え**。
4. **規範と推奨、対象範囲の取り違え**（NIST IR 8587 は民間には任意、63C-4 の単一宛先は FAL2 以上）。
5. **言い過ぎ**：「正反対」「必ず」「すべて」。原典の条件（「特に定めない限り」）を落とす。
6. **似た仕組みの取り違え**：PAR が URL から外すのは認可「要求」、認可「応答」を外すのは form_post。
7. **事故の細部**：CVE-2025-55241 の Actor token 自体は Microsoft が署名していた。署名が無かったのは、それを包んだ代理用のトークン。記事でも「暗号が破られたのではない」と正本の言い方に揃えた。
8. **数字の条件の欠落**：GraphRAG の勝率 72〜79% → 72〜83%、Lost in the Middle は TACL 2023 → 2024、全体の効果を RAG 単体の効果として書く。
9. **書籍の引き方**：主張と逆向きの記述を根拠にしていた（任意の深さの委任を管理できる、という記述を、深さを制限する主張の根拠に）。
10. **スライド間・成果物間の矛盾**（[guide-design](guide-design.md) 6 節）。
11. **用語の未定義**（読者役の点検で毎回出る）。

## 7. 記事の査読：事実と、冷たい読み

- **事実の査読**：記事の各主張を正本（ガイド・ケーススタディのリポジトリ）と照合し、「supported / 正本に無い / 言い過ぎ」を判定する。正本に無い事実は足さない。派生物（Qiita・note・SNS）は正本（Zenn）にない主張をしない。必要なら、スライドが裏づける範囲で正本に足す。
- **冷たい読み（読者役）**：前提を知らない読者として読む。用語の未定義、ラベルの無い URL の並び、コードの import の欠落、CSV の欠落などが出る。
- 指摘の採否は取りまとめ役が決め、不採用は理由を書く（「読者役の感想で、規則に当たらない」など）。原稿と記録は別のコミットにする。

## 8. 公開前の最終確認

- 個人情報・手元のパス・秘密情報の grep（[playbook/07](../playbook/07-publish.md)）。PDF のメタデータ（作成者）も見る。
- リンクが開けるか、実際に開いて確かめる。開けないもの（Zenn の公開待ちで 404 など）は共有文に入れず、その旨を伝える。
- 描画の確認は高い解像度（2560×1440）で。低い解像度ではアンダースコアが消えて見える。
- 外部 API のキーなどの秘密は、値を表示も保存もしない。使った費用は別の台帳に記録する（AgentOps の回、365 リクエストで約 0.03 ドル、上限 0.5 ドルの台帳を作った）。
