# principles/ — 基礎の考え方

`playbook/` が「何をどの順でやるか」（手順）なのに対して、ここには「なぜそうするのか」「迷ったときに何を基準に決めるか」（考え方とノウハウ）を置く。手順書だけでは、想定外の状況（ユーザーの言い直し、資料どうしの食い違い、実験が止まる、など）で判断できないため、その判断の拠り所を残す。

出典は、Advanced RAG（ガイド＋FMEA ケーススタディ）、AgentOps（ガイド＋ケーススタディ v1・v2）、JWT クレーム設計（ガイド＋ケーススタディ＋805 行の一覧表）の 3 回で実際に起きたこと。数字はその回の実測・実績。

| ファイル | 中身 |
| --- | --- |
| [research-thinking.md](research-thinking.md) | 新しい技術スタックへの向き合い方。読者の本当の問い、標準・製品・事故・権威の切り分け、情報源の重みづけ、書籍の選び方と使い方、日付 |
| [guide-design.md](guide-design.md) | ガイドの設計思想。テックリーダーが何を必要とするか、構成の理由、根拠の行と発表者ノート、言葉の規則、3 回のフィードバックから学んだこと |

| [verification-guidelines.md](verification-guidelines.md) | 検証の原則。何をもって検証済みとするか、独立したレビュー、レビュー結果の再確認、測ると言うの区別、未検証の明示、件数の数え方、繰り返し出た誤りの型 |

## 使い方

- 新しい回を始める前に、`playbook/00` と一緒に `research-thinking.md` を読む（ユーザー個人の好みと報告の型は、公開しない Claude Code のメモリに置いている）。
- ケーススタディに入る前に `casestudy-design.md` と `wsl-docker-knowhow.md` を読む。
- 「(要確認)」と付けた箇所は、記録から確定できなかったこと。次の回で確かめたら印を外す。
- 回を終えたら、新しく学んだ考え方をここに足す（手順は playbook に足す）。同じことを両方に書かない。
