# 08 教訓（これまでの回で実際に起きたこと）

## 範囲と対話

- ユーザーは途中で焦点を言い直す。最初に言い換えて確かめ、挙げられた論点を outline.md に全部転記する
- 「銀の弾丸はない」というユーザーの見立ては、ケーススタディの結論の型（共通の基準＋重点＋見送り）にそのまま使える
- 進捗を聞かれたら、終わったこと・数字・次にやることを短く。長い待ちのときは途中で一言伝える

## 調査と根拠

- 書籍は 2〜4 冊。PDF の入手方法は出版社ごとに違う（購入履歴のどこから落とすか分からないことがある）
- 公的機関の文書の位置づけを誤らない（任意の推奨を規範として書かない）
- 一次資料で自分も確かめる：サブエージェントのファクトチェックにも誤りがある

## デッキ

- サブエージェントに書かせたスライドは、表と注記の重なり・はみ出しが出る。QA の重なり検出を必ず回す
- 低解像度の PNG で文字が消えて見えるのは表示の問題。2560×1440 で判断する
- make.sh にローカルのパスを書くなら gitignore。雛形は環境変数で持たせる

## ケーススタディ

- README の件数は結果のファイルから数える（72 と書いて 67 だった）
- 実機は OSS 1 つ。商用は模擬と明記。記事で「各社の製品で測った」と書かない
- 測っていない推奨（送信者制約など）は「未検証」と表と記事の両方に書く
- 共通の基準を厳しくすると正規の要求が拒否される（誤拒否）。製品ごとの扱いが要る、という発見自体が結論になる

## 一覧表

- 列名はユーザーの用語に合わせる
- 判定の空欄は「やっていない」に見える。全セルを理由付きで埋め、validate で空欄を検査する
- 製品の対応を名前だけで埋めない
- 原典・書籍・行内・結果・スライドへのリンクを付ける（ユーザーから求められた）
- 判定の修正はスクリプト（fix_review1.py、fix_blanks.py）にして残す

## 公開と記事

- 査読で多い指摘：正本の言い方からのずれ（「署名が正しい」→「暗号が破られたのではない」）、条件の落ちた数値（「約 2 倍」→ 寿命ごとの倍率）、部分的な結果を全体として書く（契約テストで 5 つ中 3 つ）
- 件数が何を数えたか（攻撃のみか、正規の要求を含むか）を書く
- 共有文にガイドのリポジトリのリンクを入れる

## 正しさを最優先する（JWT の回の終盤）

- リンクやスライド番号の都合で訂正を弱めない。**スライドを正しくし、一覧表・README・記事のリンクを後から合わせる**（ユーザーの指示）
- 仕様の誤用が実験のコードにあったら（RFC 9396 の locations と identifier）、表記の注記で済ませずコードを直し、該当の題材を再実行して結果が変わらないことを確かめる
- 公開済みのリポジトリに作業用のファイル（仕様の全文テキストなど）が紛れていないか、公開のたびに `git ls-files` で見る

## 公開後の改訂（記事にスライドのリンクを足すだけでも）

- 正本（ガイド・ケーススタディ）を更新したら、リンクを足すだけの改訂でも記事の事実の査読をやり直す。正本の更新で付いた条件（設定の前提、「近い操作の費用」など）が記事の既存の文から落ちていた
- 読者役の出力は使い回さない。引用が原稿の今の版と食い違い、検査で止まる
- 投稿済みの SNS は、投稿時点で正しかった数値（旧版の枚数）を書き換えない。採否表に理由を書いて不採用にする

## 実測を 2 回流す（データ指向の設計の回）

- **全題材を、コードを変えずに最初からもう一度流す。** 1 回目の「5 試行で 0 件」が 2 回目に 1 件になった結果が複数あった（並べて切り替えの古い読み取り、ブローカーを戻しただけの欠落）。1 回の結果で「起きない」「一致」と書かない
- まとめ（summary）は 1 回目と 2 回目のデータで 2 度描き、機械的に突き合わせる。判定は 2 回とも満たしたときだけ「一致」。違えば「実行によって変わった」として 2 回の値を並べる。比較表（RERUN.md）もスクリプトで作る
- 「件数を合図に入れた障害だから決定的」とは限らない。送信のバッチの境目で結果が動いた（Collector の送信）。決定的なはずの欄が変わった実行を、数えて報告する
- 時間の測定は、同じ機械でも実行の日時で 2 倍ほど動いた。大小や倍率で判定するなら、中央値のしきいではなく試行の範囲が重なるかで判定する
- まとめの固定の文（手で書いた説明）は数字に追随しない。再実行で数字が動くと嘘になる。判定と読み取りの文は数字から作る
- 性質の違う群をまたいだ中央値を代表値にしない（保存域の 2.75 倍は、1.3 倍の群と 4 倍の群の間で、その値の実行は 1 つも無かった）
- 原因を推定で書いたら、それを確かめる追加の実験を足す。「CDC が遅れたのは読み取り間隔のため」は、間隔を変えた実行が無いままスライドの題になっていた。追加実験（1 回だけ、と明記）で、縮むが大小は入れ替わらない、と分かった

## 実測の結果をガイドに戻す

- 照合の表（ガイドの記述｜判定｜実測）を、まとめの中に題材ごとに持つ。ガイドへの反映は、この表の全行を 1 行ずつ対応表にしてから行う（直さない行にも理由）
- 「一次資料では確かめられなかった」点を実測しても、「確認した」とは書かない。「ケーススタディで実測した」と条件つきで書く
- 条件つきの食い違いは、ガイドの元の文を消さずに条件を足す（原典が言っていることまで実測で書き換えない）。実測の数字は注記へ
- 反映にも、別の担当のファクトチェックを入れる。反映の担当が条件を落とす（欠陥なしの条件だけの数を全体として書く、2 回の値を混ぜる）
- ガイドの題を変えたら、ケーススタディのまとめが引くスライドの題も合わせる。題の突き合わせを検査に入れておく

## 長い実行とメモリ（WSL の Docker）

- Claude Code は、待機中のバックグラウンドのシェルを、メモリが逼迫すると自動で止める（空きが 5GB あっても止まった）。長い実行は、フォアグラウンドで 1 回 9 分以内に区切り、完了済みの実行 ID を飛ばして続きから流せる作りにする
- 増えるのはコンテナではなく WSL のページキャッシュ。`wsl -u root` で `drop_caches` を区切りの間に実行すると Windows の空きが戻る（ユーザーの了承を得てから。時間の測定には直後の 1 実行に影響しうるので、実行 ID を控える）
- 止まった実行を勝手に再開しない。どこまで記録済みかを数えて報告し、続け方を選んでもらう
- 利用の上限で担当が途中で止まることがある。成果物は区切りごとにファイルへ保存させ、進捗の正本（plan.md）から再開できるようにしておく

## 一覧表（設計レビューの問い）

- 行は「実際に書いた問い」だけ。ステップ × 基盤の掛け合わせで水増ししない。そのかわり、基盤ごとに絞り込めるよう「ガイドが名指しした基盤」の列（根拠のスライドつき）と、基盤ごとの答えのシートを足す
- 実測の結びつけは、照合の行の番号で持ち、「結果の数字が、結びつけた行の文に出るか」を検査する（番号を目で数えて 1 行ずれた）
- 問いは表だけでなく、注記や箇条書きの形でも書かれている。拾う対象を表に限ると漏れる
- 凡例（構成の呼び名、実験の ID、1 回目・2 回目の読み方、判定の語）を xlsx の中に入れる。この表だけで読めること

## 記事（この回で足した点）

- 書き手にスライドと README だけで数字を取らせない。まとめ（2 回の値を併記した正本）と 1 つずつ照合させ、照合した行を報告させる
- 公開のスイッチは、査読の記録のコミットの後に立てる（publishing-hub の手順 8）。執筆の指示にスイッチを書かない
- 査読の出力に書式に無い欄があったら、検査の書式を緩めず、取りまとめ役も書き換えず、査読した本人に整えさせる
- 査読は公開済みの正本の誤りも見つける（「OSS だけ」：Redpanda と CockroachDB はオープンソースのライセンスではない）。正本を直して公開し直し、記録にその旨を書く
- 範囲の違う数を「題材の値」として書かない（Redpanda の 147 実行の最大を、Kafka の 26 実行を含む題材全体の最大として書いた）
