# 08 教訓（これまでの回で実際に起きたこと）

## 範囲と対話

- ユーザーは途中で焦点を言い直す。最初に言い換えて確かめ、挙げられた論点を outline.md に全部転記する
- 「銀の弾丸はない」というユーザーの見立ては、ケーススタディの結論の型（共通の基準＋重点＋見送り）にそのまま使える
- 進捗を聞かれたら、終わったこと・数字・次にやることを短く。長い待ちのときは途中で一言伝える

## 調査と根拠

- 書籍は 2〜4 冊。PDF の入手方法は出版社ごとに違う（購入履歴のどこから落とすか分からないことがある）
- 公的機関の文書の位置づけを誤らない（任意の推奨を規範として書かない）
- 一次資料で自分も確かめる：サブエージェントのファクトチェックにも誤りがある

## デッキ

- サブエージェントに書かせたスライドは、表と注記の重なり・はみ出しが出る。QA の重なり検出を必ず回す
- 低解像度の PNG で文字が消えて見えるのは表示の問題。2560×1440 で判断する
- make.sh にローカルのパスを書くなら gitignore。雛形は環境変数で持たせる

## ケーススタディ

- README の件数は結果のファイルから数える（72 と書いて 67 だった）
- 実機は OSS 1 つ。商用は模擬と明記。記事で「各社の製品で測った」と書かない
- 測っていない推奨（送信者制約など）は「未検証」と表と記事の両方に書く
- 共通の基準を厳しくすると正規の要求が拒否される（誤拒否）。製品ごとの扱いが要る、という発見自体が結論になる

## 一覧表

- 列名はユーザーの用語に合わせる
- 判定の空欄は「やっていない」に見える。全セルを理由付きで埋め、validate で空欄を検査する
- 製品の対応を名前だけで埋めない
- 原典・書籍・行内・結果・スライドへのリンクを付ける（ユーザーから求められた）
- 判定の修正はスクリプト（fix_review1.py、fix_blanks.py）にして残す

## 公開と記事

- 査読で多い指摘：正本の言い方からのずれ（「署名が正しい」→「暗号が破られたのではない」）、条件の落ちた数値（「約 2 倍」→ 寿命ごとの倍率）、部分的な結果を全体として書く（契約テストで 5 つ中 3 つ）
- 件数が何を数えたか（攻撃のみか、正規の要求を含むか）を書く
- 共有文にガイドのリポジトリのリンクを入れる

## 正しさを最優先する（JWT の回の終盤）

- リンクやスライド番号の都合で訂正を弱めない。**スライドを正しくし、一覧表・README・記事のリンクを後から合わせる**（ユーザーの指示）
- 仕様の誤用が実験のコードにあったら（RFC 9396 の locations と identifier）、表記の注記で済ませずコードを直し、該当の題材を再実行して結果が変わらないことを確かめる
- 公開済みのリポジトリに作業用のファイル（仕様の全文テキストなど）が紛れていないか、公開のたびに `git ls-files` で見る
