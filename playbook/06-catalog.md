# 06 付録の一覧表（xlsx）

対象の項目（クレーム、設定、ヘッダー、API など）を**出典ごとに 1 行**で網羅し、題材ごとの採否を付ける。雛形は [templates/catalog/](../templates/catalog/)。

## 列（JWT の回で自己レビューを経て決めたもの）

- **定義と出典**：No、ID、分類、名前、意味（表すこと／表さないこと）、値の型、値の数、載る場所、出典の種別、出典（節、原典にリンク）、出典 URL、書籍の該当箇所（書名・章節・印刷ページ、出版社ページにリンク）、状態（最終／草案）、変更管理者
- **製品での扱い**：製品ごとに「既定／設定で追加／独自の名前で／フック・式で可／不可・未対応／対象外（他社の独自）／不明」
- **性質**：値を書ける主体、可変性、鮮度、認可に使ってよいか、個人情報の区分、ログ方針、上限、比較規則、一意の範囲、値の語彙、同義グループ、ガイドの該当 Part（スライドにリンク）
- **題材ごと**：判定、条件、代替・関連（ID、表の行にリンク）、用途／失うこと、見直し条件、検証 ID（結果にリンク）
- **備考と確認**：備考、確認日、一次資料で確認

ユーザーの用語に合わせる（「属性」は claim の訳なので分類の列名に使わない、など）。

## 判定の値と書き方

必須（共通基準）／採用／条件付き採用／不採用・代替あり／不採用・不要／不採用・禁止／対象外

- 採用：**いつ・どう使うか**。不採用：**それで何ができなくなるか**
- 代替あり：代わりのクレームの ID。その代替は同じ題材で採用されていること（validate で検査）
- 見直し条件は**全行**（採用は判断を変える条件、対象外は関係してくる範囲の変化）
- **空欄のセルを残さない**（条件「常に」「該当なし」、検証「未検証」なども理由付きで書く）

## パイプライン

```
raw/*.json（調査担当ごと） → merge.py（ID 採番・並べ替え・製品の扱いの補完） → catalog.json
decisions/part*.json（判定担当ごと） → validate.py（全行の判定・代替の整合・空欄） → build_xlsx.py → xlsx
レビューの修正 → scripts/fix_*.py（何度流しても同じ結果）
```

## 進め方

1. 網羅：出典の種別（標準・登録簿・草案／製品／プラットフォーム／語彙）ごとにサブエージェントを分けて raw を作る。**似た項目でも出典が違えば別の行**
2. 列の自己レビュー（[prompts/column-review.md](../prompts/column-review.md)）を調査と並行で
3. 判定：方針（DECISION_POLICY.md）を先に書き、行を分けて複数の担当に判定させる
4. 判定の中身の点検（[prompts/decision-review.md](../prompts/decision-review.md)）：同義グループ内の整合、実験との整合、理由の質、個人情報、草案
5. Excel で開いて確かめる（COM で集計の数式が計算されるか、PDF に出して見た目）

## よくある誤り

- 名前だけで製品の対応を埋めて、別の仕様の同名の行に「既定」が入る（出典と載る場所で絞る）
- 代替が別の概念を指す（メールの検証状態 → 利用者 ID など）
- 構成と矛盾する文（入口が受けないトークンを「入口で読む」）
- テンプレートの差し込みで英字と日本語の間の空白が欠ける
